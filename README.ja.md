# omitnix

[English](README.md) · **日本語**

**「解析していない」が「何も無い」に見えないようにする**ことを目的にした、静的なコード目録。

> 状態: 開発初期。11 言語ぶんのアダプタが同梱されています（`pip install "omitnix[all]"`。[対応言語](#対応言語)参照）。
> どのアダプタも担当しない拡張子は `unclaimed` で、数に入り、拡張子ごとに報告され、生成物にも名前で載ります。
> アダプタが担当すると宣言していながら読めなかったファイルは `unknown` で、1 件ずつ名指しされ、
> リポジトリがそう頼んだときだけ実行を失敗させます（`fail_on_unknown`）。
> これは個人の趣味の制作物で、**サポートはありません。**

```
pip install "omitnix[all]"
omitnix                                # .omitnix/index.json を書き出す
omitnix --version                      # いま入っている版
pip install --upgrade "omitnix[all]"   # 更新するとき
```

## これは何か

`omitnix` はコードベースを走査し、生成物 `.omitnix/index.json` を 1 つ書きます。中身は 2 つです。

- ファイル単位の索引（機能概要・認証・認可の確認・読むテーブル・書くテーブル）
- テーブルから、それを触っているファイルへの逆引き

データベースには接続しません。スキーマが要るときは、別のツールが出力した JSON を読みます。

以前は同じ事実を人が読む形にした `.omitnix/index.md` も書いていましたが、2026-09 に廃止しました。
別のツール（[OpenWiki](https://github.com/langchain-ai/openwiki)）が `index.json` を読んで
読みやすい文書を書くようになったためです。1 組の事実に描画器が 2 つあると必ずずれていきますし、
実際のリポジトリでは平たい表が 3,538 行に育って誰も開いていませんでした。
`omitnix` は証拠を書く側に専念し、人が読む文書は他所の仕事にしています。

## LSP や MCP では駄目なのか

**多くの用途では、駄目ではありません。** 置き換えを狙っていません。
分かれ目は 1 つだけで、**「0 件」という答えを受け取ったとき、それが何を意味するか**です。

「`orders` テーブルを書き換えているのはどのファイルか」と聞いて、何も返ってこなかったとします。

**LSP（言語サーバー）**の「参照 0 件」は、*シンボル*の参照が見つからなかったという意味です。
`"UPDATE orders ..."` のように文字列の中にあるテーブル名は、そもそも探す対象に入っていません。
そして構文解析に失敗したファイルが何本あったとしても、**その数は答えに付いてきません。**
それは 1 ファイルずつの診断として出るだけで、合計する仕組みがどこにもありません。

**MCP 越しの検索**の「見つかりませんでした」は、**どこまで探したかを言いません。**
それを読んだ AI は、「無い」と「探していない」を区別できず、たいてい「無い」と読みます。

`omitnix` は同じ 0 件を返したうえで、次を同じ成果物に入れます。
読めなかったファイルの名前と理由、担当するアダプタがいなかった拡張子とその件数、
そして解釈できなかった文があった場合は「このテーブル一覧は足りていないかもしれない」という一文です。

**違いはこれだけで、しかも取引は双方向です。** LSP は型を見た定義・参照・改名をファイルをまたいで行います。
このツールはそれを一切しませんし、間接呼び出しは意図的に 1 段で止めます。
MCP のサーバーは自由な質問に対話で答えます。このツールには質問を受ける口がありません。書くのはファイル 1 つです。

| | LSP / MCP の道具 | `omitnix` |
|---|---|---|
| 答え | その場限り。セッションが終われば消える | **コミットされるファイル。**生成元のコミットが刻まれ、差分が見え、レビューできる |
| 要るもの | 言語ごとのサーバー、多くは依存が解決済みであること | **Python 3.11 と `pip` だけ。**ビルドもデータベースも常駐も不要 |
| 単位 | 1 ファイル・1 シンボル・1 プロジェクト | **リポジトリ全体、またはディレクトリ配下の全リポジトリ**（52 リポジトリで実測） |

**競合ではなく、下に敷くものです。** `omitnix` は事実**とその限界**を `index.json` に書きます。
それを AI へ配るのは MCP サーバーの仕事、人が読む文書にするのは別のツールの仕事で、
OpenWiki は既にこれを読んでいます。ここでは何も質問に答えません。
**探される側に、自分がどこまでを覆っているかを言わせる**だけです。

**「この一覧、全部載っているのか」で時間を失っていないなら、ここに用はありません。**
効くのは 3 つの場面です。AI に読ませる索引を置きたいとき（欠けを伝えなければ、AI は無い行を「無い」と読みます）。
新しく入るコードに、その言語が報告できるはずのものが付いているかを機械で止めたいとき。
そして、リポジトリが人の記憶に収まらない数あるときです。

## なぜ作ったか

生成された目録を作ること自体は簡単です。難しいのは、それを正直な状態に保つことです。

パーサが理解できないファイルが 1 つ足された瞬間、たいていのツールはそれを黙って飛ばします。
行が単に存在しなくなり、**行が無いことは「これは存在しない」と読まれます。**
人にとってもそうですし、生成物を読む AI にとってはなおさらです。
そして目録がいちばん薄いのは最も新しいコードで、そこは同時に、
確認されていない認可経路が最も残りやすい場所でもあります。

そこで `omitnix` は、網羅性そのものを成果物として扱います。

```
発見数 == 解析済み + 未解決 + 読めなかった + 担当なし
```

解析器が追えなかったもの（実行時に組み立てられる SQL、1 段を超える間接呼び出し）は、
空欄ではなく理由付きの `unresolved` として残します。
まったく解析できなかったファイルは後ろの 2 つのどちらかで、
この 2 つの違いは「不具合」と「ごく普通のこと」の違いです。

- **`unknown`** — アダプタがその拡張子を担当すると宣言していながら、記録を作れなかったもの。
  読めないバイト列、UTF-8 でない、正しいはずのソースを文法が拒んだ、アダプタが落ちた。
  何かがおかしいので、**1 件ずつパスと理由を名指し**します。
- **`unclaimed`** — その拡張子を担当するアダプタがいないので、そもそも何も試していないもの。
  文章、設定、画像、書庫、そしてまだアダプタを書いていない言語。
  何もおかしくないので、列挙せず**拡張子ごとに数えます**。

```
omitnix: 20 discovered file(s) are claimed by no adapter, so nothing tried to read them.
  .md x5, .scm x5, .yml x4, (no extension) x3, .yaml x2, .toml x1
```

2026-09-11 まではこの 2 つは同じ状態でした。実際のリポジトリでは、それは 192 ファイルが
1 行ずつ並ぶことを意味し（`.md` が 95、`.json` が 45、`.png` が 7）、
本物の失敗はその途中のどこかに埋もれていました。
**変わっていないのは、どちらも数に入り、どちらも `index.json` に名前で載ることです。**
誰も見ていないファイルも、そのリポジトリが持っているファイルであることに変わりはありません。
それを自分の合計から黙って落とすツールは、自分が防ぐために作られたはずの嘘をついています。

`unknown` が実行を**失敗させるか**は別の話で、既定では失敗させません（`fail_on_unknown: true` で有効）。
`unclaimed` は何があっても失敗させません。報告すべき不具合がそこに無く、誰にも直しようがないからです。

失敗を無条件にしていたのは、名指ししておく価値のある間違いでした。
それは、すべての欠けを宿題に変えてしまいます。
リポジトリが緑になるには、どのアダプタも担当しないものそれぞれについて、
設定ファイルへ理由の 1 文を書くしかありませんでした。
実際のリポジトリで測ると、52 件の除外設定のうち 36 件はそのためだけに存在していました。
「PNG は program source ではない」は誰かが下した判断ではなく、ツールが要求した事務作業です。
このリポジトリ自身の設定も、2 つの状態を分けた日に 16 行減りました。

さらに悪いことに、**リポジトリ側では閉じようのない欠けもあります。**
自分のアダプタが担当すると言っている言語の、正しいソースを読めない文法は*このツールの*不具合です。
それでビルドを落とすのは、正しいコードを書き換えるか、嘘の理由を書くかの二択を迫ることになります。

欠けが隠れないことを担保しているのは、**生成物がそう言っていること**です。これは常に成り立ちます。
実行を失敗させるのはその上に乗る方針で、
失敗を読む人に何かできることがある場面でだけ意味を持ちます。
[新規ファイルの門](#新規ファイルの門)が、自分が手を打てる対象について厳しいままなのはそのためです。

実行のたびに同じカバレッジ行が出て、`index.json` にも同じ数字と、生成元のコミットが入ります。

```
Coverage: 202/255 analyzed, 8 unresolved, 0 unknown, 45 unclaimed
```

```json
{
  "generated": { "commit": "0123456", "dirty": false, "tool": "omitnix", "partial": false, "tracked_only": true },
  "coverage": { "discovered": 255, "analyzed": 202, "unresolved": 8, "unknown": 0, "unclaimed": 45 }
}
```

`--check` が 2 つの実行を比べるとき、`generated` の大半は比較から外れます。
コミットと dirty 旗はコミットのたびに変わり、それは目録が古いかどうかとは無関係だからです。
`tracked_only` だけは例外で、これは**発見が何という問いに答えたか**を記録しているので、
別の問いに答えた 2 つの生成物が等しいと判定されてはいけません。

そして、このツールは「未使用」とは言いません。言うのは
**「この解析器が、このコミットで、静的な参照を観測しなかった」**です。

### 逆引きに見えていないもの

テーブルの `read_by` / `written_by` は、**読み取れた範囲**であって、リポジトリが実際にしていることではありません。
そこから 2 つのことが従い、どちらも読み手に推測させず `index.json` に書き込まれます。

- あるテーブルを触っていて、かつ解析器が読めなかった文も持っているファイルは、
  そのテーブルの **`unresolved_in`** に名前が載ります。その項目は下限であって総量ではないので、
  名指しされたファイルを見に行ってください。
- **唯一の言及が、誰も読めなかった文だったテーブル**には、そもそも行がありません。
  行が無いので印も付けられません。この場合は、該当する一覧の横で、実行全体につき 1 回数えます。

```json
"table_gaps": {
  "files": ["api/orders_export.php"],
  "unresolved_count": 1,
  "note": "1 statement in 1 file could not be read, so the table list may be incomplete: ..."
}
```

すべての文が読めた実行では `note` は空、`unresolved_count` は `0` です。
同じ文は標準エラーにも出ます。テーブル一覧は、ファイル記録を開かない人が引用する側の半分だからです。

これは 2026-09-11 に、実際のリポジトリへツールを向けて見つかりました。
sqlglot が解釈できなかった全文検索の句が 1 つあり、そこがあるテーブルを読む唯一の場所だったのに、
逆引きは「何も読んでいない」と言っていました。

### すべての項目が持つ 5 つの状態

ファイル単位の各項目（機能概要・認証・認可・読むテーブル・書くテーブル）は、
`index.json` の中に `state` を持ちます。**空に見える値から読み手が状態を推測することはありません。**

| `index.json` の `state` | 意味 | 見え方 |
|---|---|---|
| `out_of_scope` | そのファイルを扱ったアダプタが宣言した能力の外。値の欠落ではない | `{"state": "out_of_scope"}` — `value` キーそのものが無い |
| `not_configured` | アダプタはこの能力を宣言しているが、リポジトリが何を探すかを言っていないので、何も探していない。`.omitnix.yaml` の関数名を対象とする `authentication` と `authorization` が該当 | `{"state": "not_configured"}` — `out_of_scope` と同じく `value` キーが無い |
| `none_observed` | アダプタがこの能力を宣言していて、探して、このコミットでは見つからなかった。「未使用」ではない | `{"state": "none_observed", "value": []}` |
| `value` | 普通の結果。アダプタが完全だと確信している空リストを含む | `{"state": "value", "value": [...]}` |
| *(項目の状態ではない)* | ファイル自体が解析されていない。`fields` は `{}` で、`reason` が理由を言う。`status` は `"unknown"`（アダプタが担当すると言って読めなかった。`coverage.unknown` に数え、標準エラーで名指しし、`fail_on_unknown` が作用する唯一の対象）か `"unclaimed"`（担当するアダプタがいない。`coverage.unclaimed` に数え、拡張子ごとに報告） | ファイル記録の最上位の `"status"` と `"reason"` |

`not_configured` はいちばん新しい状態で、**このツールが自分自身についてこれを間違えた**ので存在します。
2026-09-11、`.omitnix.yaml` の無いリポジトリへ向けたとき、618 ファイル全部に
`authorization: none_observed` と報告しました。これは
「618 ファイルを確認し、1 つも認可呼び出しを持っていなかった」と読まれます。
何も確認していませんでした。`authorization_functions` が空だったので、探索対象が無かったのです。
**何も探していない空リストは発見ではありません。** 今はそう書きます。
門はずっと同じ区別をしていて、リポジトリが定義していない確認は、拒否ではなく飛ばします。

## 例

設定は走査される側のリポジトリに置きます。ツールの中にプロジェクト固有の値は焼き込みません。

```yaml
# .omitnix.yaml
include:
  - "api/**/*.php"
  - "batch/**/*.php"
exclude:
  - "vendor/**"
  - "node_modules/**"
authorization_functions:
  - apply_visibility_filter
authentication_functions:
  - require_session
schema_snapshot: schema.json
```

ツールが書くのは `index.json` です。同じ事実は、たとえば次のような表として読めます
（スキーマは架空で、**この表は `omitnix` が出力するファイルではありません**。
この文書を読む人のためにここに置いてあります）。

| ファイル | 機能概要 | 認証 | 認可 | 読む | 書く | 状態 |
|---|---|---|---|---|---|---|
| `api/orders_list.php` | ログイン中の顧客の注文一覧 | あり | あり | `orders`, `customers` | — | analyzed |
| `api/orders_export.php` | 注文を CSV で書き出す | あり | あり | `orders` | — | unresolved (dynamic_sql) |
| `batch/reindex.py` | 夜間の再索引 | — | — | `orders` | `search_index` | analyzed |

## 使い方

```
omitnix                       # 全量実行。.omitnix/index.json を書く
omitnix --all-files           # git の追跡対象ではなく、作業ツリー全体を対象にする
omitnix --check               # 何も書かず、生成物が古ければ失敗する
omitnix --files a.php b.php   # 明示した一覧だけを解析（pre-commit フックが渡す形）
omitnix --gate --files a.php  # そのうち新規追加のファイルだけを確認する
omitnix --gate --since main   # このブランチが追加したものを確認する（CI 向けの形）
omitnix --print api/x.php     # 1 ファイルの記録を JSON で出す
omitnix --workspace ~/code    # ディレクトリ配下の全 git リポジトリ（下記）
```

差分実行もキャッシュもありません。**毎回すべて作り直すことで、
出力が古いかどうかという問い自体を消しています。**
その代償はファイルの数ではなく大きさで決まります。支配的なのは構文解析なので、
普通のソースなら 1 秒を大きく下回り、非常に大きな生成ファイルを数本持つリポジトリでは相応に時間がかかります。
このプロジェクト自身での実測（2026-09-08）は 57 ファイルで 0.5 秒でした。

`--files` はその部分集合について報告し、既定では何も書きません。
**部分実行が、全量の索引をその一部で上書きしてはいけない**からです。
それが望みなら `--write` を付けてください。

`--check` は目録を比べ、`generated` の大半（コミット、dirty 旗）は比べません。
コミットが進んだというだけで失敗しないようにするためです。`generated.tracked_only` は比べます。

### 全量実行が何を発見するか、そして既定を変えた理由

素の `omitnix` は **git が追跡しているもの**を発見します。
これはワークスペース実行がずっと使ってきた既定と同じで、
ファイルシステムを歩いて出てくるもの全部ではありません。
`--all-files` はその歩き方を要求するもので、単一リポジトリでも `--workspace` の中と同じ挙動になります。

以前は逆でした。単一リポジトリ実行は無条件に作業ツリーを歩き、git に尋ねるのは `--workspace` だけでした。
つまり同じツールが、どちらのモードかによって別の問いに答えていて、しかも単一実行側の既定が誤りでした。

これは `omitnix --check` を実際のリポジトリの CI に組み込んで見つかりました。
コミットされていた `.omitnix/index.json` は開発機で生成されたもので、
その作業ツリーには git が追跡していないファイルが 66 個ありました。
生成物、他のツールの作業用ディレクトリ、コミットするつもりの無い置き忘れです。
**まったく同じコミットをきれいに取得した CI にはそれらが 1 つもありません。**
そこでの新規実行は 738 ファイルを発見し、索引は 803 と言っており、
`--check` はそれらを `removed` と報告して、目録が古いこととは無関係な理由でジョブが落ちました。
索引はそもそもリポジトリから再現できるものではなかったのです。

追跡対象だけを既定にする代償は、ワークスペースの既定が既に払っているものと同じです。
**まだ `git add` していない新しいファイルは、全量実行からは見えません。**
これはきれいな取得から同一に再生成できるべき文書にとっては正しい取引で、
[新規ファイルの門](#新規ファイルの門)にとっては誤った取引です。
門は git に別の問いを立てていて（「作業ツリーで何が新しいか」）、この発見経路をまったく使いません。
門だけが、全量実行から見えなくなった未追跡ファイルを見続けるのはそのためです。

### 終了コード

| コード | 意味 |
|---|---|
| 0 | 実行が終わった。読めなかったものは隠されずに報告された |
| 1 | 発見したファイルが `unknown` で、**かつ** `fail_on_unknown` が設定されている |
| 2 | 使い方、設定、またはアダプタ契約の誤り |
| 3 | `--check` が生成物の古さを検出した |
| 4 | `--gate` が新規追加のファイルを拒否した |

`unclaimed` は `fail_on_unknown` が何と言おうと 1 を出しません。
何も読もうとしていないので、報告すべき失敗がありません。数には入り、生成物にも載ります。

`--workspace` は同じコードを多数のリポジトリにまたがって使います。
実行できたリポジトリのどれかが `unknown` を持てば 1、
そもそも実行できなかったリポジトリがあれば 2 です。
両方起きたときは 2 が勝ちます。**何も実行できなかったリポジトリは、大きさの分からない穴**だからです。

## 新規ファイルの門

全量実行は「全部解析できたか」を問います。`--gate` は、
最もそれが必要なファイルについて、より厳しい問いを立てます。
**いま追加されようとしているファイルは、自分のアダプタが報告できるものを欠いたまま入ってきてはならない。**

新しいコードは目録がいちばん薄いところです。機能概要はまだ無く、
認可呼び出しは最も忘れられやすく、パーサがそもそも理解できなければ、
**書かれたその日に穴として索引へ入ります。**

```
$ omitnix --gate
omitnix: noted: theme.unmapped: unclaimed (no adapter claims '.unmapped')
omitnix: gate refused 3 files newly added in the working tree
  orders_purge.flow: no authorization call (adapter 'flow' observed no call to any authorization function listed in authorization_functions)
  broken.flow: unknown (adapter 'flow' raised SyntaxError: unexpected token)
  undocumented.flow: no summary (adapter 'flow' reports summaries and found none here)
```

**新規**とは、未追跡か、追加として `git add` されているかのどちらかです。
以前は存在しなかったファイルがレビューに届く経路はこの 2 つです。
追跡済みのファイルは、どれだけ大きく書き直されても新規ではありません。改名も新規ではありません。
git の作業ツリーの外では、門は合格ではなく誤りを報告します。
**「新しいものは無い」と「判断できなかった」は別の答え**だからです。

### 作業ツリーではなく、範囲について尋ねる

上の問いは、ファイルがまだコミットされていない間しか答えを持ちません。
そのため門は単体では pre-commit フックの中で動きますが、**フックは 1 台ずつ有効にするもの**です。
有効にしていない人がコミットしたファイルは、他の誰かの目に触れるころには追跡済みで汚れも無く、
以後誰からも門を通されません。
**全員のローカル設定の和集合であるような網羅性は、誰にも言明できません。**

`--since` はもう一方の問い、サーバーが立てられる側の問いを立てます。

```
$ omitnix --gate --since origin/main
omitnix: gate refused 1 file added since origin/main
  reports/export.php: no authorization call (adapter 'php' observed no call to any authorization function listed in authorization_functions)
```

比較は merge base に対して行うので、ブランチ上では「このブランチが追加したもの」を意味します。
プルリクエストの基点に対して CI で走らせれば、誰の機械がどう設定されていようと、
追加されたファイルはすべて門を通ります。
フックはフックが得意なこと、つまり push の前に教えることをすればよく、唯一の砦である必要はなくなります。

参照が解決できないとき（浅い取得が典型）、門は誤りを報告して非ゼロで終了します。
**何も追加されなかった、とは決して報告しません。**
確認されていない push に対する緑の実行こそが、これが防ごうとしている失敗だからです。
GitHub Actions では取得時に `fetch-depth: 0` を指定してください。

**何が必須かは、アダプタの能力宣言から決まります。ファイルの言語からは決まりません。**
認可呼び出しを報告できないアダプタに、それが求められることはありません。
これは、スタイルシートのアダプタを足した日が、
**新しいスタイルシート全部が、持ちようのない確認を欠いて門に落ちる日**になるのを防ぎます。
そして、欠けていることが不具合であるような能力だけが必須になります。
テーブルを 1 つも読まないファイルは普通であって、欠陥品ではありません。

`unknown` だけは例外で、これを和らげるものはありません。
アダプタが担当すると言ったのに読めなかったのですから、参照すべき能力宣言がそもそもありません。
それを黙って通すことが、このツールが存在する理由になっている失敗そのものです。

他の 2 つは**記録するが拒否しない**もので、合格でも不合格でも毎回出ます。
黙って合格する門は、確認した内容以上のことを語ってしまうからです。

```
omitnix: noted: batch/reindex.php: unresolved (dynamic_sql) (the table name is built at run time)
omitnix: noted: docs/release.md: unclaimed (no adapter claims '.md')
```

`unresolved` は、解析器がファイルを読んだうえで一部を追えなかったことを言います。
実行時に組み立てられる SQL、1 段を超える呼び出しなど、書いた人には直せない**このツール側の限界**です。
これで拒否すると、誰もファイルを編集して解除できない形で作業が止まります。
**満たしようのない門は、切られる門です。**

`unclaimed` は、`unknown` と同じ状態だったころは拒否していました。
分離した後もそれを続けると、自分の文章を除外するのをやめたリポジトリ
（文章はもう実行を落とさないので、やめられるようになりました）では、
**新しい `.md` が全部 pre-commit フックに拒否される**ことになります。
README を足しただけで発火する門は、やはり切られる門です。
新しい `unclaimed` ファイルに必要なのは見えていることで、それは満たされています。
ここに出て、カバレッジ行に出て、`index.json` に名前で載ります。

### 免除

確認が本当に当てはまらない場面はあります。
意図的にセッション無しで到達できる公開の入口などです。理由を添えて、そう書いてください。

```yaml
gate_exemptions:
  - paths: ['api/health_check.php']
    skip: [authentication, authorization]
    reason: Public liveness endpoint, deliberately reachable without a session.
```

**理由は必須の項目であって、注釈ではありません。**
理由の無い項目は設定の誤りになり、理由は免除が発火するたびに毎回印字されます。
書いて正当化できない免除、あるいは二度と誰の目にも触れない免除は、
門が静かに意味を失っていく仕組みそのものです。
免除で `unknown` を黙らせることはできませんし、門が行っていない確認を切ることもできません。

既存のファイルが門に誤って引っかかるときに直すのは、免除一覧ではなく規則のほうです。

## 多数のリポジトリをまたぐ

`--workspace DIR` は `DIR` 配下のすべての git リポジトリを 1 コマンドで実行します。
これは単一リポジトリ実行の**上に乗る層**であって、より広い実行ではありません。
各リポジトリは単独で実行したときとまったく同じように解析され、
ワークスペースは結果の識別と集約を担当します。

```
omitnix --workspace ~/code --dry-run                # 何が走るかを並べる。何も書かない
omitnix --workspace ~/code                          # 実行する。./.omitnix-workspace/ に書く
omitnix --workspace ~/code --exclude-repo vendored  # ひとまとまりを飛ばし、飛ばしたと言う
```

**走査される側のリポジトリには何も書きません。**
すべて 1 つの出力先（`--out`、既定 `./.omitnix-workspace/`）へ行きます。
全体の要約と、リポジトリごとの生成物が 1 つずつです。
ワークスペースにあるリポジトリの多くは他人の一日に属するもので、
そこへ生成ファイルを撒くのはこのツールの仕事ではありません。
それが望みなら `--write-per-repo` で明示的に頼んでください。

### 一意でなくなる 3 つのもの

| | 1 つのリポジトリの中 | ワークスペース全体 |
|---|---|---|
| ファイルの鍵 | ルートからの相対パス | `<リポジトリ>/<パス>` |
| テーブルの名前 | 逆引きの存在理由そのもの | **決して統合しない** |
| ファイルの内容 | 鍵ではない | 鍵ではない |

1 つ目は机上の話ではありません。ここで測った 52 リポジトリでは、937 個の相対パスが
複数のリポジトリに存在し、うち 1 つは 22 リポジトリに重複していました。
素のパスを鍵にしていたら、36,958 件の記録のうち 1,063 件が**黙って互いに統合されて**いたことになります。

2 つ目は見た目より深刻です。ある系の `orders` と別の系の `orders` が静かに同じ行を共有するのは、
自信満々で静かな誤りです。同じ測定で、133 個のテーブル名が複数のリポジトリに出現していました。
そのため逆引きは出自のリポジトリの中に留まり、
全体の要約は 1 つに統合した表ではなくリポジトリごとの件数を報告します。

3 つ目は、**内容ハッシュによるキャッシュを持たない**理由です。
バイト単位で同一の 2 ファイルが違う結果に解析されることがあります。
`require __DIR__ . '/queries.php'` はディレクトリが違えば別のファイルに解決されます。
内容を鍵にしたキャッシュは、片方のリポジトリの答えをもう片方のファイルに渡してしまい、
**出力にはその痕跡が何も残りません。**
重複する仕事は、状態を持たない `--jobs` で処理します。

### 既定で何を見るか

git が追跡しているファイルから、ビルド出力・依存ツリー・文章・宣言的データ・
バイナリ資産・鍵と証明書を除いたものです。
これに同意しないリポジトリは自分の `.omitnix.yaml` を書きます。
`exclude_defaults: false` と書いたリポジトリは書かれたとおりに歩かれ、ワークスペースは何も足しません。

### どこに配備されていて、古くなっていないか

```
omitnix --workspace ~/code --status
```

コードを解析するのとは別の問いです。
**どのリポジトリがコミット済みの索引を持っていて、最後にコミットされたのはいつで、
それがまだソースと一致しているか。** どこにも何も書きません。

```
repository                             index       applied     analyzed    pointed at by
----------------------------------------------------------------------------------------
alpha                                  current     2026-09-11  49/74       CLAUDE.md+AGENTS.md
beta                                   -           -           -           -
gamma (worktree)                       STALE       2026-09-02  314/737     -
```

コミット済みの索引が古ければ終了コード 3 です。理由は `--check` と同じで、
**古い生成物は、見つけた人に現状として読まれる**からです。
この実行が確認する装備を持っていなかった索引についても 3 を返します。
「確認できなかった」と「確認して問題なかった」が同じ終了コードでよいのは、
誰も何にも繋がない調査だけです。

この報告が気を付けていることが 4 つあります。

**ソースを読めなかった実行は、索引を古いと呼ばずに、読めなかったと言います。**
素の `pip install omitnix` には言語の文法が入っていないので、
ソースは全部 `unknown` になり、生成物はすべて不一致になります。
それを「古い」と報告することは、**良い索引を空同然の索引で置き換えろという助言**です。

```
repository                             index       applied     analyzed    pointed at by
----------------------------------------------------------------------------------------
alpha                                  UNVERIFIED  2026-09-11  2/74        CLAUDE.md+AGENTS.md

omitnix: could not be checked: alpha
  this run could not read 49 file(s) the committed index has an answer for, so a
  difference would say more about this machine than about the index.
  Install what it needs with: pip install "omitnix[go,html,python,tsjs]"
```

助言は、そのリポジトリに必要だと分かった追加分を**全部 1 つのコマンドで**名指しします。
最初に出会った 1 つを出して、次の実行でまた次の 1 つを出す、という形にはしません。

**索引を持たないリポジトリも、省かずに並べます。**
「30 件を調べて 9 件が持っている」と「9 件ありました」は別の主張です。
解析されるのは実際に索引を持っているリポジトリだけなので、
大きな木を調べる費用は、実際に配備されている数だけかかります。

**比較は単一リポジトリ実行**であって、ワークスペース実行ではありません。
コミット済みの索引はそのリポジトリの中でツールを走らせて作られたものなので、
より狭い実行と比べると全リポジトリが「古い」と出ます。
これは鮮度の調査が最も間違えてはいけない答えです。
また `generated.commit` を `HEAD` と比べることもしません。
**生成物はコミットされる前に書かれる**ので、正しく保守されている索引は常に 1 つ前のコミットを指し、
その判定はすべてを古いと呼びます。

**linked worktree はそれと言います。**
別のリポジトリではありません。設定もフックもオブジェクトストアも元の木と共有していて、
違うのは取り出しているブランチだけです。
そこで索引を作り直せと言うのは、内容が普通は merge で届くブランチに修正を向けることなので、
報告はコマンドを出す代わりに主たる作業ツリーの場所を言います。

最後の列は、`CLAUDE.md` / `AGENTS.md` が `.omitnix/index.json` を名指ししているときにその名前が出ます。
**どの指示ファイルにも書かれていない索引は運で見つかるもので、運は網羅性ではありません。**

「git が追跡しているファイル」はワークスペース専用の規則ではありません。
`--workspace` を使わない単一リポジトリ実行も同じ既定です。
ワークスペース固有なのはこの節の追加の除外（ビルド出力・文章・宣言的データ・バイナリ資産）だけで、
単一リポジトリは自分のツール既定（`vendor/`、`node_modules/`、`dist/`、`.git/`）と
`.omitnix.yaml` が足したものを保ちます。

既定は推測ではなく実測です。1 台の機械上の 52 リポジトリで（2026-09-08）:

| 対象 | 発見数 | うち担当アダプタなし |
|---|---|---|
| 作業ディレクトリ、ツール既定のみ | 139,764 | 96,931 |
| 作業ディレクトリ、＋ワークスペース既定 | 67,838 | 26,408 |
| **追跡ファイル、＋ワークスペース既定**（既定） | 36,958 | 1,129 |

拡張子の一覧では表現できない最大の塊はビルド出力と取り込んだ依存で、
既定がディレクトリから始まるのはそのためです。
その次に大きかったのは、あるリポジトリの 24,436 個の無視される作業ファイル
（データベースのデータ領域とブラウザのプロファイル）で、
既定の対象が git の追跡対象である理由がこれです。
`--all-files` は代わりに作業ディレクトリを歩きます。

**これらの判断はすべてリポジトリごとに数えられ、報告されます。**
大きさが見えない除外は、調査が静かに何も覆わなくなっていく仕組みです。

### 設定していないことは、発見ではない

認可関数の名前に既定値は置けません。リポジトリごとに違うからです。
1 つも名前を挙げていないリポジトリは**未設定**として報告され、そう列挙され、実行のたびに明言されます。

```
omitnix: 52 repositor(y/ies) name no authorization function, so no authorization check
was made in them. This is not a finding that they have none.
```

実行できなかったリポジトリは、それ自身の数として数えられ、決してゼロとして畳み込まれません。
そのファイル群は量の分からないものであり、
**その量をゼロと呼ぶことは、このツールが防ごうとしている間違いのリポジトリ大の版**です。

## 契約の確認と、その限界

索引はファイルが何をしているかを言います。
ファイルが何を*しなければならなかったか*は言えません。
呼び出しが必ずあること、直接アクセスが禁じられていること、といった話です。
それは semgrep の仕事で、[`.semgrep/`](.semgrep/) に、
すべて架空の名前で書いた規則の例が入っています。

**semgrep を索引の構築に使うことは決してありません。**
grep 型の規則から組み立てた索引は、規則が想定しなかったものを落とします。
それこそがこのツールが不可能にしようとしているものです。

例の規則は例のファイルに対して実行済みです（semgrep 1.176.1、Windows 11、2026-09-08）。
すべての規則が `orders_export.php` で発火し、`orders_list.php` では 1 つも発火しません。
なお **semgrep は発見があっても終了コード 0 を返します。**
発見でジョブを落としたいなら `--error` を付けてください。
コマンドと Windows での並列度の実測は `.semgrep/README.md` にあります。

これらの規則には本物の限界があります。semgrep CE にはファイルをまたぐ解析が無いので、
PHP では一度に 1 つの関数しか見えません。

- *表現できる*: 「この関数は認可関数を呼んでいない」
- **表現できない**: 「呼んでいる関数が、実際にクエリを制限している」

2 つ目には型とファイル横断の呼び出しグラフが要ります。それは **PHPStan のカスタム規則**の領分で、
omitnix は意図的にそこへ踏み込みません。配線も同梱していません。
その保証が要るなら、semgrep の規則を伸ばして行えない確認をほのめかすのではなく、そちらで書いてください。

## 対応言語

アダプタは 3 段階に分かれていて、**その段は宣言であって、黙って適用される制限ではありません。**
各アダプタは自分が埋められる列を明言し、それ以外の列は空欄ではなく `n/a` として描かれます。
そのため、スタイルシートが
「認可呼び出しを確認されて、無かったファイル」として表示されることはありません。

| 段 | アダプタ | 報告するもの |
|---|---|---|
| 完全 | `php`, `python`, `go`, `tsjs`, `sql` | 機能概要・認証・認可・読むテーブル・書くテーブル |
| 逆引き | `html` | 機能概要と、画面が要求する宛先 |
| 最小 | `css`, `rust`, `shell`, `powershell`, `vue` | ファイルが存在すること、および先頭のコメント |

| アダプタ | 拡張子 | 導入 |
|---|---|---|
| `php` | `.php` `.phtml` | `omitnix[php]` |
| `python` | `.py` `.pyi` | `omitnix[python]` |
| `go` | `.go` | `omitnix[go]` |
| `tsjs` | `.ts` `.tsx` `.js` `.mjs` `.cjs` | `omitnix[tsjs]` |
| `sql` | `.sql` | `omitnix[sql]` |
| `html` | `.html` `.htm` | `omitnix[html]` |
| `css` `rust` `shell` `powershell` `vue` | `.css` `.rs` `.sh` `.ps1` `.vue` | 導入不要 |

導入の列は、依存が無いときに実行が告げる内容でもあります。
文法を読み込めなかったアダプタが担当するファイルは `unknown` になり、
その理由は**追加分の名前**を挙げます。取り込みに失敗した配布物の名前ではありません。
`pip install tree-sitter` ではなく `pip install "omitnix[python]"` です。
この 2 つは同じ助言ではありません。
追加分は binding と文法と sqlglot をまとめて入れ、配布物はそのうち 1 つを入れます。
後者に従った読み手は、次の実行で次の足りないものを告げられ、その次の実行でさらに次を告げられます。
**毎回正確で、1 ファイルを読むのに 3 回の実行が要ります。**

`tsjs` は他が出さない列を 1 つ報告します。**画面 → API**、
つまりそのファイルが `fetch` や `axios` を通じて要求する宛先です。
`html` は同じ列を、フォームの action、スクリプトの src、ページ内のスクリプトから報告します。
それが目録の普段の読まれ方、**「どの画面がこの入口を呼んでいるか」**の向きであり、
HTML が他に何も報告しないアダプタを持つ価値がある理由です。

最小の段が存在するのは、**リポジトリが含んでいる拡張子を無視するのは無料ではない**からです。
アダプタの無い言語は `unclaimed` になります。数えられ、そして 1 ファイルについても何も語られません。
これを測った 55 リポジトリのうち `.sh` は 37 件、`.ps1` は 30 件に現れました。
何も語ることのないコードベースの量としてはかなり多く、
30 リポジトリ分のその沈黙より、ここに置く 3 ファイルのほうが安いということです。

2026-09-11 まで、この論拠はもっと強く、そしてもっと悪いものでした。
担当の無い拡張子は、それを持つすべてのリポジトリで誰かが除外設定を書くまで、実行を毎回落としました。
アダプタの代わりが事務作業だったわけです。その方は直りました。
だからこの段は、代わりに**何を報告するか**で存在価値を示す必要があります。

段は証拠が尽きるところで止まります。Rust が最小なのは、
測定対象の Rust リポジトリがどれもデータベースの crate を宣言していなかったからです。
テーブルの抽出器を書いても、試す相手がありませんでした。
**本物の試し相手ができたときに上がるのであって、その前ではありません。**

## アダプタを書く

言語を足すことは**ファイルを足すこと**で、本体を編集することではありません。
`omitnix/adapters/` にモジュールを置いて実体を公開すれば、発見の仕組みが見つけます。

```python
from omitnix.adapters.base import Adapter, AnalysisRequest, AnalysisResult
from omitnix.model import Capability


class IniAdapter(Adapter):
    name = "ini"
    extensions = (".ini",)
    capabilities = frozenset({Capability.SUMMARY})

    def analyze(self, request: AnalysisRequest) -> AnalysisResult:
        first = request.text.splitlines()[0] if request.text else ""
        return AnalysisResult(values={Capability.SUMMARY: first.strip("; ")})


ADAPTER = IniAdapter()
```

アダプタは自分が作れる能力を宣言し、本体はそれ以外を要求しません。
この宣言が、スタイルシートを「認可の確認を欠いたファイル」として報告させないものです。
